# 开发规范

## 基本原则

- 所有修改必须保持在当前仓库内，不读取或修改只读备份目录。
- 优先修复根因，避免临时兼容层、重复实现和无验收标准的重构。
- 修改前先阅读目标模块及其测试，保持现有行为；无法保持时必须补充迁移说明和测试。
- 不提交运行时生成物、用户数据、构建产物或本地调试文件。

## TypeScript 与 React

- 使用严格类型，避免 `any`；边界输入使用类型守卫或显式校验。
- 组件负责展示和交互，持久化、协议转换、业务计算放在 store/service/utils 中。
- Hook 保持单一职责；副作用必须有明确的生命周期和错误处理。
- 共享类型放在 `src/shared` 或对应领域的 `types` 中，避免 Renderer 与 Electron 各自复制类型。
- 保持现有模块边界，不为了方便把领域逻辑放进全局 store 或入口文件。

## Electron 与 IPC

- preload 只暴露最小、类型明确的 API，不直接暴露 Node 能力。
- 新增或修改 IPC channel 时，同时更新 shared 类型、preload、主进程 handler 和测试。
- 所有来自 Renderer 的参数必须在主进程校验；使用现有 IPC 错误包装和来源校验。
- 不在 Renderer 直接访问文件系统、SQLite、原生模块或环境变量。

## 数据与错误处理

- SQLite 是运行时配置和项目数据的唯一后端；旧 JSON 只用于一次性迁移和用户主动导入/导出。
- 数据库写入必须经过 repository；跨表修改使用事务。
- 动态对象存入 SQLite TEXT 前序列化，读取后在应用层校验并提供默认值。
- 不静默吞掉错误：可恢复错误记录日志并使用默认值；不可恢复错误向上抛出。
- 用户输入、外部协议响应和导入文件都视为不可信数据。

## UI 与样式

- 侧栏树保持紧凑、层级清晰，目录和用例不得重复渲染。
- 优先使用项目已有设计 token、组件和图标，避免随意新增颜色或视觉规则。
- 交互状态必须覆盖加载、空数据、错误和禁用状态。
- 使用 Prettier 格式化 TypeScript、TSX、CSS、JSON、SQL、Markdown 和配置文件。

## 测试

- 新功能至少包含核心逻辑测试；持久化、IPC、迁移和导入导出必须覆盖成功与失败路径。
- 修复 bug 时先增加能复现问题的回归测试，再修改实现。
- 优先运行目标 suite，再运行 `npm run test:api`、类型检查、lint、IPC 检查和构建。
